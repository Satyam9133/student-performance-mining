# Project Explanation (in simple language)

## 1. Problem statement
Colleges record attendance, marks and study habits, but nobody looks at all of them together to spot who is doing well and who may need help. We want a system that learns from past student records and predicts a student's **performance class** - Excellent, Good, Average or Poor.

## 2. Why this project was created
It is a hands-on Data Mining case study. The original work used WEKA (a desktop tool). This project rebuilds the same workflow as a website so the steps are visible, interactive and explainable.

## 3. Objectives
1. Load and explore a student dataset. 2. Clean it. 3. Visualize relationships. 4. Train and compare classifiers. 5. Evaluate with a confusion matrix and metrics. 6. Show decision-tree rules. 7. Predict for an individual student and explain the result - always as *decision support*, not a verdict.

## 4. Dataset
1,525 synthetic records (1,500 students + 25 duplicates) with Attendance, Internal/Assignment/Practical/Midterm/Previous marks, Study_Hours, Class_Participation, Backlogs and the class **Performance**. It was generated by `scripts/generate_dataset.py` from hidden "ability" and "discipline" scores plus noise, so attributes relate to each other realistically but accuracy is never 100%. Problems (missing values, duplicates, impossible values, messy labels) were added on purpose so preprocessing has real work.

## 5. Features of the website
Ten pages: Dashboard, Dataset Explorer (with CSV upload), Preprocessing, Visualization, Training, Comparison, Prediction, Decision Tree, Evaluation, About. Every figure is computed live from the data.

## 6. Data preprocessing
Raw data is not ready for learning. We:
- **Standardise labels** (`good `, `GOOD` → `Good`).
- **Remove rows without a class** - we cannot learn from a student whose answer is unknown.
- **Remove duplicates** - the same student counted twice would bias the model and leak into the test set.
- **Fix impossible values** (attendance 130%) by treating them as missing.
- **Handle missing values** by filling with the median (robust against extreme values), the mean, or dropping rows.
- **Exclude Student_ID** - an ID has no meaning for performance.
- **Encode / scale** - text categories become 0/1 columns (one-hot); numbers are standardised only for KNN, which uses distances.
The page shows *before vs after* (e.g. 1,525 → 1,497 rows, 250 → 0 missing) and the models are trained on the *after* data.

## 7. Classification
Classification means assigning a record to one of several predefined classes. The algorithm learns from labelled examples (training data) and then predicts the class of new students.

## 8. Decision Tree (J48 / C4.5 idea)
A decision tree asks a series of yes/no questions about attributes ("Internal marks ≤ 65?") and follows the answers down to a leaf holding the predicted class. At every step the algorithm picks the attribute that best separates the classes - measured by **entropy / information gain** (C4.5 uses a gain-based criterion). Every path from top to leaf is an IF-THEN rule, which makes trees easy to explain. In WEKA this is **J48**; here we use scikit-learn's `DecisionTreeClassifier` with the entropy criterion, a minimum leaf size and a depth limit (to avoid over-fitting). It is *similar to* J48, not identical.

## 9. Naive Bayes
Uses Bayes' theorem: P(class | attributes) ∝ P(class) × ∏ P(attribute | class). "Naive" because it assumes attributes are independent of each other. Fast and simple.

## 10. KNN
To classify a student, find the **K = 7** most similar students in the training data (by distance over all attributes) and let them vote. Needs scaled attributes, otherwise large-valued attributes dominate.

## 11. Random Forest
Builds 100 different trees on random samples of the data and averages their votes. One tree can be unstable; many trees together are usually more accurate but harder to read.

## 12. Train/test split
We hide part of the data (20% or 30%) from the model while it learns, then test on it. Testing on data the model has already seen would hide over-fitting. The split is **stratified**, so every class appears in the same proportion in both parts.

## 13. Cross-validation
The data is split into k folds (default 10). Each fold takes a turn as the test set while the model trains on the others; the scores are averaged. This is more reliable than one split. It is WEKA's default way to evaluate J48.

## 14. Confusion matrix
A table where **rows are real classes and columns are predicted classes**. The diagonal is correct predictions; other cells show which classes get confused (e.g. Good vs Average).

## 15-18. Accuracy, Precision, Recall, F1
- **Accuracy** = correct predictions ÷ all predictions.
- **Precision** (for a class) = of students predicted as that class, how many truly are.
- **Recall** = of students who truly are in the class, how many we found.
- **F1** = balance (harmonic mean) of precision and recall.
Accuracy alone can mislead when classes are unequal, so we show all four.

## 19. How prediction works
1. You enter values in the form. 2. The browser sends them to `POST /api/predict`. 3. The backend validates ranges, builds one row, and the trained pipeline fills gaps, encodes, and classifies. 4. The model returns a probability for each class; the highest is the prediction, and its probability is the **confidence**. 5. To explain, each input is replaced one at a time by the dataset's typical value; if confidence in the predicted class drops, that input was supporting the prediction. These influences describe the *model*, not the real cause of anyone's results.

## 20. Frontend / backend architecture
- **Frontend (React + Vite + Tailwind + Recharts):** pages that call the API and draw charts, tables and the tree.
- **Backend (Flask):** REST endpoints (`/api/dataset`, `/api/upload`, `/api/preprocess`, `/api/train`, `/api/predict`, …) returning JSON.
- **ML layer (pandas + scikit-learn):** cleaning, pipelines, training, evaluation, explanation.
- **Storage:** the CSV file; trained models live in memory. Vite proxies `/api` to Flask so no CORS setup is needed.

## 21. Academic support insights
Predicted students are placed in temporary groups - *Performing Well, On Track, Needs Attention* - and, if needed, shown suggestions such as "Improve attendance" based on which attributes are below the typical Good/Excellent student. This is decision support to start a conversation, not a permanent label.

## 22. Limitations
Synthetic data; the model learns patterns, not causes; predictions can be wrong; a single tree is less accurate than ensembles; state is in memory; student data must be anonymized; results must be reviewed by humans.

## 23. Future scope
Real anonymised data, hyper-parameter tuning, SHAP explanations, semester trend tracking, teacher login, SQLite storage, PDF report export, handling class imbalance.
